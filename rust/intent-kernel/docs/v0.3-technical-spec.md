# Intent Kernel v0.3 Technical Specification

## Purpose

v0.3 turns the current prototype into a safer foundation without rewriting the whole system. The project already has useful primitives: intent parsing, plan compilation, capability metadata, execution, proof logging, memory, LLM generation, negotiation, and reflexion. The v0.3 goal is to make their boundaries explicit and prevent invalid or unknown plans from reaching execution.

## Architecture Map

| Layer | Current Modules | Decision | Notes |
| --- | --- | --- | --- |
| Cognitive Core | `intent`, `compiler`, `plan`, `eval`, `agi`, `intelligence::reflexion` | Retain and refactor | Keep deterministic intent-to-plan compilation as the stable core. Keep reflexion as experimental verified generation. |
| Memory | `memory`, `intelligence::knowledge_base` | Retain, normalize later | Both stores are useful. A single memory schema is deferred until the runtime contract is stable. |
| Execution/Capability | `capability`, `executor` | Retain and harden | Capability definitions must match executor behavior. Unknown capabilities must fail, not pass as stubs. |
| Verification/Proof/Safety | `security`, `proof`, `verify`, `runtime::PlanValidator` | Retain and harden | Validation happens before execution. Proof events remain append-only and hash-linked. |
| Runtime | `runtime`, CLI orchestration in `main` | Add thin boundary | v0.3 introduces a plan validation gate without replacing the existing CLI flows. |
| LLM | `llm`, `negotiation`, `solution_gen`, `self_review` | Retain as adapters/experiments | LLM output remains downstream of safety and verification. |
| UI | `main` | Retain CLI | A richer UI, TUI, daemon, or service API is deferred. |

## Retain

- `ProofLedger` and hash-chain verification.
- `Executor` snapshot/rollback behavior for file writes.
- `CapabilityRegistry` as the actuator contract source.
- `SecurityGateway` prompt-injection and capability blocking checks.
- `MemoryStore` and `KnowledgeBase` as simple JSON-backed stores.
- Ollama-backed `LLMClient` with template fallback.
- Reflexion and negotiation flows as experimental coding workflows.

## Refactor Now

- Add a runtime validation gate before execution.
- Register every executor-supported capability in the capability registry.
- Add required-input metadata for capabilities.
- Reject unknown capabilities instead of treating them as successful stubs.
- Wire `SelfReviewer` into the reflexion loop so the existing module is no longer dead code.
- Align project version labels to `0.3.0`.

## Delete Or Avoid

- Do not keep silent success paths for unimplemented capabilities.
- Do not merge MUKTI/MUATO/TITAN/Nexus concepts as large new subsystems yet.
- Do not introduce a database, scheduler, service mesh, vector store, or multi-agent runtime until the core validation contract is stable.

## Defer

- Unified long-term memory schema and retrieval ranking.
- Approval UX for high-risk plans.
- A typed plan DSL with topological execution.
- Tool sandboxing beyond the current capability checks.
- Rich UI/API surface.
- Persistent runtime state machine.
- Formal proof objects beyond hash-linked event records.

## v0.3 Runtime Contract

Before any plan executes, the runtime must verify:

- The plan has at least one node.
- `entry_node` exists.
- Node ids are non-empty and unique.
- Edges reference existing nodes.
- Capabilities are registered.
- Capability-required inputs are present.
- Forbidden or dangerous capabilities are rejected.
- Unreachable nodes are reported as warnings.

## Implementation Roadmap

1. Foundation safety: runtime plan validation, registry/executor alignment, unknown capability rejection, focused tests.
2. Plan quality: replace placeholder compiler plans with typed plan builders that include concrete inputs.
3. Human approval: add an approval record type and CLI flow for irreversible or high-risk plans.
4. Memory normalization: merge mission memory and reflexion knowledge into one schema with stable ids and provenance.
5. LLM hardening: isolate prompts, response cleaning, verification, and retry policy behind a single LLM workflow boundary.
6. Runtime orchestration: add a small runtime state machine for `planned`, `validated`, `approved`, `executing`, `verified`, `rolled_back`, and `completed`.
7. UI/API: expose the same runtime contract through CLI first, then optionally TUI/service once core behavior is reliable.
